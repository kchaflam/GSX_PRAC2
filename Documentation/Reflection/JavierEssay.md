# Reflection Essay - Javier

The most challenging aspect of this assignment was understanding how to move from a simple application running on one machine to an infrastructure that can be reproduced, scaled, and explained as a complete system. At first, Docker, Docker Compose, Kubernetes, Terraform, CI/CD, and network design felt like separate topics. The hard part was not only learning the syntax, but understanding why each layer exists and how they connect in a real organization.

Docker was the first step where this became clear. Containerizing the Nginx service and the Python backend showed me why consistency matters. If the application runs inside a container with its dependencies, the environment becomes much easier to control. I also learned that a Dockerfile is not just a list of commands to make something run. The base image, copied files, instruction order, and user permissions all affect security, size, and maintainability.

Docker Compose was probably the easiest tool to understand, but it was also very useful because it made the relationship between services visible. Running Nginx and the backend separately is possible, but Compose makes the whole stack easier to start, stop, configure, and test. The health checks and service dependency made me think about startup order and reliability. Before this assignment, I would have considered a container "working" if the process was running. Now I understand that a service should also prove that it is actually responding correctly.

Kubernetes was the part that surprised me the most. At first it felt more complicated than necessary for such a small application, especially compared with Docker Compose. However, after working with Deployments, Services, ConfigMaps, probes, resource limits, and NetworkPolicies, I understood that Kubernetes is designed for a different problem. It is not only about starting containers, but about keeping the desired state of the system alive. If a pod fails, Kubernetes can replace it; if a service needs to scale, the Deployment can create more replicas.

Terraform was another important learning point. At first I did not fully understand why we needed Terraform if Kubernetes manifests already describe infrastructure. The main idea I learned is that Infrastructure as Code makes deployment more reproducible and easier to manage over time. Keeping infrastructure in version control means the setup can be reviewed, repeated, and improved like application code.

The network design part also changed my perspective. I used to think of networking mainly as IP addresses and connectivity, but this assignment showed me that network design is also a security decision. Separating development, staging, production, partners, DMZ, and management areas reduces the impact of mistakes or attacks. The Kubernetes NetworkPolicies made this more practical because they start from the idea that only necessary traffic should be allowed.

If I started the project again, I would plan the repository structure and the environment strategy earlier. Some parts were developed step by step, which helped us learn, but it also meant that later we had to organize documentation, manifests, Terraform files, and network policy files so that the whole project made sense together. I would also test each layer more systematically before moving to the next one.

My understanding of DevOps and cloud-native systems has changed a lot. I now see DevOps less as a single tool and more as a way of connecting development, operations, automation, security, and documentation. A good system is not only one that works once on one laptop. It should be reproducible, documented, and understandable by another person.

What I would like to learn more about is production Kubernetes. In this assignment we used Minikube, which is good for learning, but a real environment would include ingress controllers, TLS certificates, secrets management, persistent storage, monitoring, and cloud provider integration. Overall, this assignment gave me a clearer picture of how modern infrastructure is built and why each decision matters.
