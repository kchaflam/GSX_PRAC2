# Reflection Essay - Kevin Andrés Chafla Moran

The most difficult part of this assignment was figuring out how all the different tools fit together in one system. At first, Docker, Kubernetes, Terraform, networking, and infrastructure concepts all felt like separate topics that didn’t really connect. As I worked through the project, it became clearer that real infrastructure is basically the combination of all of them working together as one automated setup. Understanding how containers, orchestration, infrastructure as code, and deployment workflows interact required a shift in thinking compared to normal application development.

Kubernetes was probably the hardest part technically. Docker Compose is much more straightforward because everything runs locally and the configuration is easier to follow. With Kubernetes, there are many new concepts like pods, deployments, services, namespaces, ConfigMaps, probes, and NetworkPolicies. On top of that, debugging is more complicated because a single issue can come from different layers, like networking, labels in YAML files, or service configuration. Once I understood how Kubernetes manages pods automatically and restarts them when they fail, it made more sense why it is used in production systems.

Another challenging part was understanding Terraform and how it fits into infrastructure management. At first, it was not very clear why it is needed if Kubernetes already allows defining infrastructure through YAML files. However, I learned that Terraform works at a higher level and is used to define and provision infrastructure resources in a more structured and repeatable way. Even though I did not go very deep into advanced Terraform usage, I understood the main idea of Infrastructure as Code and how it helps keep infrastructure consistent, version-controlled, and easier to reproduce. The main difficulty was understanding where Terraform ends and where Kubernetes begins in a real system.

What surprised me most was how important automation and consistency are in modern infrastructure. Before this project, I thought infrastructure was mostly about manually managing servers. After working with Terraform and Kubernetes manifests, it became clear why Infrastructure as Code is so important. It makes everything reproducible, easier to manage, and less dependent on manual setup. I also didn’t expect networking and security to be such a big part of it. It’s not just about running containers, but also controlling how they communicate and isolating environments properly.

If I had to start again, I would spend more time planning the structure before writing any configuration. At the beginning, I focused on making individual components work, but later I had to reorganize files and adjust things to make Kubernetes and Terraform concepts fit together properly. A clearer structure from the start would have reduced a lot of debugging and rework.

Overall, this project changed how I see DevOps and cloud-native systems. It’s not just about deploying applications automatically, but about combining development, infrastructure, security, and operations into one workflow. Everything is designed to be scalable, repeatable, and automated from the beginning.

The area I’d like to explore more is Kubernetes in more depth, especially security and production-level setups. Things like NetworkPolicies, ingress controllers, monitoring, and secret management seem really important in real systems. I’d also like to see how all of this is done in real cloud platforms like AWS or Azure, since this project was mostly focused on a local Minikube environment.
